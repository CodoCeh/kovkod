# Спецификация: Extended Clipboard (картинки в буфере обмена)

## Контекст

Сейчас буфер обмена между Android-приложением и Linux-рабочим столом синхронизируется
через классический RFB clipboard (`ClientCutText`/`ServerCutText`, тип сообщения 6/3) —
он умеет передавать только текст (протокольное ограничение, не баг реализации).
Сервер TigerVNC на столе уже поддерживает более новое расширение протокола —
Extended Clipboard pseudo-encoding, которое умеет передавать и другие форматы, включая
картинки в виде DIB (Device Independent Bitmap — растровые данные без файлового
заголовка BMP). Задача — реализовать эту же поддержку в Android-клиенте, не трогая
сервер (R04), сохранив рабочим текстовый путь (R03).

## R01/R02 — цель: картинки идут через буфер обмена

### R01.1 Согласование возможностей происходит один раз за сессию, сразу после RFB-инициализации
Критерий приёмки: после успешного handshake клиент отправляет и получает Caps-сообщение
Extended Clipboard; результат (поддерживает ли собеседник картинки) хранится в памяти
на время текущего RFB-соединения, повторно не запрашивается.

- **Первый запуск.** До завершения Caps-обмена текстовый путь работает как раньше
  (R03) независимо от исхода согласования картинок; попытка скопировать картинку до
  завершения согласования — no-op (как сейчас), без очереди на отправку.
- **Отказ.** Сервер не заявил поддержку Extended Clipboard в списке кодировок или
  Caps не пришёл — клиент остаётся на классическом `CutText` только для текста;
  никакой ошибки пользователю не показывается, это штатный откат.
- **Границы.** Согласование — свойство соединения, не приложения: при переподключении
  (новый RFB-хендшейк) выполняется заново.

### R02.1 Копирование картинки из Android-приложения (галерея и т.п.) уходит на стол
Критерий приёмки: пользователь копирует фото из Галереи → на рабочем столе Linux
`Ctrl+V` в любое приложение вставляет ту же картинку.

- **Кривой ввод.** `ClipData`, где `getText()` возвращает непустую строку — это
  текст, картиночная ветка не трогается (текст в приоритете, дублирования нет).
  `ClipData` без текста, но с `Uri`, чей MIME не начинается с `image/` — вне
  области задачи, no-op (см. границы R08).
- **Отказ.** Собеседник не заявил формат DIB в своих Caps — картинка не отправляется,
  событие тихо игнорируется (не откатываться на попытку прислать как текст).
- **Рост.** Если декодированная картинка (DIB, несжатая) больше объявленного
  собеседником максимума для непрошенной отправки (`maxUnsolicitedSize` из Caps) —
  отправка пропускается, а не режется/масштабируется незаметно для пользователя.
  Автоматическое сжатие/downscale — вне объёма этой задачи.
- **Формат передачи.** Исходящий DIB-блок сжимается zlib перед отправкой (симметрично
  распаковке на приёме, R02.2) — без этого сервер не разберёт Provide-сообщение и
  весь путь Android→стол не будет работать, несмотря на формально пройденные шаги
  выше; это обязательная часть критерия приёмки, не деталь реализации на усмотрение.
- **Границы конвертации.** Прозрачность (альфа-канал) и поворот по EXIF не
  обрабатываются отдельно — пиксели переносятся в DIB как есть, без специальной
  логики; если это даст видимо неверный результат на части фото — это принятое
  ограничение объёма, а не пропуск. Декодирование очень крупных фото перед упаковкой
  делается стандартным Android `Bitmap`-декодированием без отдельной защиты от
  нехватки памяти сверх уже описанного ограничения по `maxUnsolicitedSize`.

### R02.2 Картинка, присланная со стола, попадает в Android-буфер обмена
Критерий приёмки: пользователь копирует изображение на столе (`Ctrl+C` в просмотрщике
или файловом менеджере) → в любом Android-приложении `Вставить` показывает эту же
картинку.

- **Пусто.** Нет активной подписки на этот путь, если Extended Clipboard не
  согласован — тогда ничего не приходит, что штатно (см. R01.1 «Отказ»).
- **Кривой ввод / отказ.** Битый/усечённый DIB-блок (ошибка распаковки zlib,
  некорректные размеры в заголовке) — данные отбрасываются с записью в лог
  приложения; RFB-соединение не рвётся из-за одного плохого clipboard-сообщения.
- **Прерывание.** Процесс декодирования не пишет временный файл частями — либо
  собран валидный PNG и опубликован как `ClipData`, либо не публикуется ничего.
  Недописанных/битых файлов в кэше не остаётся.
- **Потом.** Временный файл под картинку живёт в кэш-директории приложения
  (`cacheDir`), не в постоянном хранилище — старые файлы можно чистить как обычный
  кэш, отдельного механизма ротации не требуется на этом объёме.

## R05/R06 — слой протокола (`RfbClient.java`)

### R05.1 Клиент заявляет и распознаёт pseudo-encoding Extended Clipboard
Критерий приёмки: в `SetEncodings` уходит код pseudo-encoding Extended Clipboard наравне
с уже используемыми (`Raw`, `CopyRect`, `DesktopSize`); входящие `ServerCutText`
с отрицательной длиной распознаются как Extended Clipboard, а не как ошибка протокола.

### R06.1 Поддерживаются два формата данных: Text и DIB
Критерий приёмки: битовые флаги форматов Text/DIB выставляются в Caps так, чтобы текстовый
путь остался рабочим (R03) даже если DIB не согласован ни у одной из сторон.

- **Границы.** Другие форматы Extended Clipboard (RTF, HTML, Files) — вне объёма
  задачи; флаги для них не выставляются, код для них не пишется (не имитируем
  поддержку, которой нет). Задел под их будущее добавление отдельно не
  проектируется — это не запрошено брифом.

## R07/R08/R09 — мост Android ↔ RFB (`DesktopView.java`)

### R07.1 Существующий текстовый мост не меняет поведение
Критерий приёмки: `OnPrimaryClipChangedListener` и `CutTextListener` продолжают
синхронизировать текст точно так же, как до этой задачи (регресс-проверка, не
новая функциональность).

### R08.1 Чтение картинки из `ClipData` (Android → стол)
См. критерии в R02.1 выше — это его техническая реализация.

### R09.1 Запись картинки в `ClipData` (стол → Android)
См. критерии в R02.2 выше — это его техническая реализация.

## Не входит в объём (явные границы)

- Файлы произвольного типа через буфер (формат `Files` Extended Clipboard) — не
  запрошено в брифе.
- RTF/HTML — не запрошено.
- Изменение сервера TigerVNC — бриф констатирует, что сервер уже поддерживает
  расширение (R04), и просит только клиентскую часть — трогать сервер незачем.
- Даунскейл/сжатие крупных изображений сверх честного соблюдения `maxUnsolicitedSize` —
  не запрошено, поведение при превышении — тихий пропуск (см. R02.1 «Рост»).
