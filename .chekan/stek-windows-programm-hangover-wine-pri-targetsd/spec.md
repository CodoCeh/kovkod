# Спецификация: Стек Windows-программ (Hangover/Wine) при targetSdk 36

## 1. Контекст и архитектура

На Android при `targetSdk 36` SELinux-домен `untrusted_app` запрещает `execmod` (изменение прав отображённых файлов с записью на исполнение). Стандартный Wine/Hangover мапит PE-образ из файла, патчит релокации и вызывает `mprotect(+EXEC)`, что немедленно блокируется ядром.

Для решения проблемы используется механизм загрузки PE в безымянную память (`MAP_ANONYMOUS`), активируемый флагом `removable = TRUE` в `map_image_into_view` unix-части `ntdll.so`. Безымянная память разрешена для исполнения во всех приложениях (`execmem`).

## 2. Требования и поведение

### R01: Стек Windows-программ (Hangover/Wine)
- Поддержка запуска Win32/x86/x64 приложений на aarch64 через Hangover.
- Запуск осуществляется в окружении proot Debian 13 trixie.

### R02: Сохранение targetSdk 36
- Приложение `ru.codoceh.stol` сохраняет `targetSdk 36` (требование Google Play).
- Домен исполнения остаётся `untrusted_app` без использования run-as или отключения SELinux.

### R03: Загрузка PE в анонимную память
- Unix-библиотека `ntdll.so` (сборка из `tools/hangover/ntdll.so` с маркером `CodoCeh anon-PE loader`) подменяет стандартную библиотеку Hangover.
- При загрузке секций PE `removable = TRUE` принудительно заставляет загрузчик читать данные через `pread` в анонимную память.

### R04i: Установка стека по требованию из магазина
- Базовый образ системы не содержит сотен мегабайт пакетов Wine/Hangover.
- При первом запуске Windows-игры или приложения из Магазина (`store/backend.py`), магазин устанавливает Hangover и автоматически подменяет `ntdll.so` на нашу патченную версию.

### R05i: Сквозная приёмка и тесты
- Скрипт `tests/e2e/windows-apps.sh` проверяет установку стека из магазина, валидирует сборку `ntdll.so`, проверяет домен `untrusted_app` и успешное открытие окна Windows-приложения.
